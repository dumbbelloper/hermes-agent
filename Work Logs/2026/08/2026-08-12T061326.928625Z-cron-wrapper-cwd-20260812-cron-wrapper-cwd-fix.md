## 사용자 요청과 목적

사용자는 오늘 Hermes cron이 실행된 것처럼 보였지만 Telegram 알림, GitHub PR, commit이 없었던 이유를 확인해 달라고 요청했다. 목적은 scheduler 실행과 실제 결제 뉴스 수집 작업을 구분하고, 실행이 조기에 차단됐다면 원인을 수정하는 것이다.

## 수행한 조사

- `hermes cron runs b83df32a868f --limit 10`으로 오늘 자동 실행 5건을 확인했다.
- cron output 5개와 `agent.log`를 대조했다.
- execution DB에서 오늘 실행 시간이 모두 약 0.05초임을 확인했다.
- `.hermes-news/data`에서 2026-08-12에 생성·수정된 source state, raw snapshot, automation run이 없음을 확인했다.
- GitHub PR, remote automation branch, 오늘 commit, Telegram delivery ledger를 확인했으며 신규 side effect가 없었다.
- Hermes scheduler 구현의 `_run_job_script()`를 확인해 pre-run script cwd가 job workdir이 아니라 `~/.hermes/scripts`인 것을 확인했다.
- 설치된 wrapper를 `~/.hermes`와 project root에서 각각 실행해 `controller_missing` 및 repository gate 차이를 재현했다.

## 근본 원인

[hermes-news-autonomy-wrapper.py](../../../Automation/hermes-news-autonomy-wrapper.py)는 `HERMES_NEWS_WORKSPACE`가 없을 때 `Path.cwd()`를 workspace로 사용했다. Hermes scheduler는 pre-run script를 script parent directory에서 실행하므로 wrapper는 `~/.hermes/Automation/autonomy.py`를 찾았고, `{"wakeAgent": false, "reason": "controller_missing"}`를 즉시 반환했다. scheduler output은 reason을 보존하지 않고 일반 `wakeAgent=false`로 기록하므로 겉으로는 정상 no-change 실행처럼 보였다.

## 수행한 변경

- wrapper가 환경변수가 없을 때 sibling `hermes-news-autonomy.workspace` sidecar에서 repository 절대 경로를 읽도록 변경했다.
- `HERMES_NEWS_WORKSPACE` 환경변수 우선순위를 유지했다.
- sidecar가 없거나 읽을 수 없을 때만 기존 cwd fallback을 유지했다.
- scheduler cwd가 repository 밖이어도 sidecar를 통해 controller를 실행하는 회귀 테스트를 추가했다.
- 설치 문서에 wrapper mode `0700`, workspace sidecar mode `0600`과 설치 절차를 반영했다.

## 내린 결정과 근거

- scheduler 내부 구현을 project에서 수정하지 않고 repository wrapper를 수정했다. 이 작업의 배포 범위와 소유권이 project wrapper에 있고, Hermes 자체 upgrade와 충돌하지 않는 최소 수정이기 때문이다.
- workspace 절대 경로를 wrapper 코드에 하드코딩하지 않고 owner-only sidecar로 분리했다. 다른 설치 경로에서도 재사용하고 repository binding 검사를 그대로 유지하기 위해서다.
- source delta가 없었다고 결론 내리지 않았다. 오늘 실행은 source precheck 전에 `controller_missing`으로 종료되어 공식 출처를 조회하지 않았기 때문이다.
